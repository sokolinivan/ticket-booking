# План реализации TicketBooking MVP

## Цель

Реализовать TicketBooking как **модульный монолит** на .NET 10 с двумя отдельными frontend-приложениями:

- `public-web` — клиентский интерфейс;
- `admin-web` — административный интерфейс.

Вся система доступна через единую точку входа `TicketBooking.Gateway` на YARP. Backend состоит из `TicketBooking.Api`, `TicketBooking.Worker`, `TicketBooking.DatabaseMigrator` и набора изолированных бизнес-модулей. Основное хранилище — PostgreSQL с отдельной схемой на модуль.

# Рекомендуемый порядок поставки вертикальных срезов

Чтобы не реализовывать все слои горизонтально до появления работающего продукта, после создания платформенного каркаса рекомендуется поставлять функциональность вертикальными срезами:

1. **Admin: создание компании и мероприятия**.
2. **Public: просмотр опубликованного мероприятия**.
3. **Admin: настройка сеанса, тарифа и capacity**.
4. **Customer identity: регистрация и вход**.
5. **Public: создание и отмена заказа**.
6. **PaymentEmulator + подтверждение оплаты**.
7. **Outbox + выпуск билета**.
8. **Public: мои заказы и билеты**.
9. **Admin: просмотр заказов, оплат и билетов**.
10. **Audit + эксплуатационные инструменты**.

Каждый вертикальный срез должен включать backend, необходимый frontend, миграцию базы, telemetry и автоматические тесты.

# Критерии готовности MVP

- [ ] Клиент может зарегистрироваться и войти.
- [ ] Администратор может войти отдельно от клиента.
- [ ] Администратор может создать компанию и мероприятие.
- [ ] Администратор может создать сеанс и тариф с ограниченной вместимостью.
- [ ] Клиент видит опубликованные мероприятия.
- [ ] Клиент может создать заказ при наличии мест.
- [ ] Конкурентные заказы не приводят к overselling.
- [ ] Неоплаченный заказ можно отменить и он может автоматически истечь.
- [ ] PaymentEmulator может подтвердить или отклонить оплату.
- [ ] Повторный payment callback не ломает состояние заказа.
- [ ] Оплата подтверждается только через integration callback, а не browser redirect.
- [ ] После успешной оплаты `Reserved` переводится в `Sold`.
- [ ] После успешной оплаты через outbox выпускается билет.
- [ ] Клиент видит свои билеты.
- [ ] Критические административные действия записываются в audit log.
- [ ] public/admin frontend доступны через единый Gateway origin.
- [ ] Система поднимается локально через Aspire.
- [ ] Compose генерируется из AppHost и проходит CI validation.
- [ ] Unit, integration, architecture, system и browser tests проходят в CI.
- [ ] В Git, логах, аудите и Compose нет секретов.
